## G1 speed gap (Keras compiled trainer 88 ms vs our stateless jit 111 ms, Polaris b32)

What Keras does differently (`SP/keras/src/backend/jax/trainer.py`): `make_train_function` wraps `train_step` in
`jit(step_fn, donate_argnums=0, out_shardings=...)`, i.e. it DONATES the whole state tuple (trainable, non-trainable,
optimizer, metric variables); test and predict functions donate too. Everything else is the same as the spike's
`jax-stateless` mode (stateless_call + value_and_grad + stateless_apply). `train_on_batch` does more host work, not less:
it syncs the state back into all variables after every step (`jax_state_sync`) and updates the loss tracker.

Effect of donation in the compiled program (CPU, spike graph dim 64, 4+2 layers, 1814 state arrays,
`S5_g1_probe.py`): without donation the program copies 429 pass-through state arrays (unchanged ntv leaves such as beta
and bitwidth state) into fresh output buffers and allocates new buffers for every output; with donation the outputs alias
1728 inputs (`input_output_alias`). On a GPU each copy is a kernel and each fresh buffer an allocation plus a deferred
free of the old one, a per-array host cost independent of the batch, which matches the G1 gap being nearly constant
(18, 18, 20, 23 ms at b4/8/16/32). Not verified on a GPU (no GPU here).

CPU timings, median (p10) ms/step of 30 after 3 warm-up; each cell is one process. Run 1 (`g1_cpu.log`) on a quiet
machine; runs 2 and 3 (`g1_cpu2.log`, `g1_cpu3.log`) while another agent loaded the CPU (load average 8), so their
spreads are wide (p90 up to 660 ms). Run 3 is after `grad_norm` became opt-in.

|---|---|---|---|---|

| `TrainStep` (this stage) | | 74.2, 76.0 / 75.7, 83.5 | | 406.1, 431.5 / 430.9 (400.0), 431.4 (411.1) |

Reading: at b4 the donating steps (spike or `TrainStep`) are 5-15% faster than Keras' trainer on CPU, as the plan's
spike found (< 7%). At b32 the differences (up to ~8%) are inside the run-to-run spread of the loaded runs; the p10 values
agree to 2-5%. A CPU cannot show the A100 gap, which is a fixed ~20 ms per step.

So: `TrainStep` donates by default (`donate=True`) and returns the gradient norm only on request (`grad_norm=True`, it
duplicates the clipping's reduction); `test_state_donation_and_model_variables` checks that the donated buffers are
consumed, the Keras variables survive (`init_state` and `assign_to_model` copy), and `donate=False` keeps them. **G3 must
time `TrainStep(donate=True)` against `donate=False` and against Keras' `train_on_batch` on the A100** (S6b `17_g3_step`);
if a gap remains, profile with `jax.profiler` before anything else.

## EBOPs and beta (plan 3.6)

- Read-out `penalty / beta`, where `penalty` is the sum of the EBOPs terms of `stateless_call(return_losses=True)`. Not
  `sum(losses) / beta` as the plan wrote: the loss list ends with one term per regularized trainable weight (Keras
  `Layer.losses` = add_loss terms, then `_get_regularization_losses()`), independent of beta (0.335 of 804.9 at the prod
  spec; 2.886 of 3.137 on the generated model at beta 1e-12). `EbopsLeaves.split_losses` drops that tail
  (`n_regularizers` = trainable weights with a regularizer). `test_loss_list_is_ebops_terms_then_regularizers` shows:
  with EBOPs off exactly the regularizer terms remain and equal the tail; every front term is > 0; one term per leaf.
- `TrainStep.train_step` returns `penalty` and `regularization` separately (`StepOutput`); `TrainStep.ebops(out, beta)`
  divides. It needs the beta the step ran with (the state is donated, so read it before the step).
- Beta: one value written to every leaf's `_beta` slot of `ntv` (same shape and dtype), so no retrace. `read_beta`
  refuses mixed betas; `ebops_readout` refuses beta <= 0.
- `train_step` toggles `_enable_ebops` on every leaf while tracing (static `ebops_on`), and restores the flags.

## Optimizer (plan 3.7), deviations from torch / Lightning

1. beta1 fixed at 0.9 (user decision); torch `OneCycleLR` cycles it 0.95 -> 0.85 -> 0.95 for AdamW and Lion
   (asserted in `test_onecycle_equals_torch_at_20_steps`).
2. Keras evaluates an LR schedule at its micro-step counter `_iterations` (`base_optimizer._get_current_learning_rate`);
   `OneCycleLR(steps_per_update=k)` divides, so the LR changes per optimizer step as in Lightning. Adam's bias correction
   uses `iterations = _iterations // k` (Keras), as torch.
3. AdamW epsilon placement (Keras adds eps to sqrt(v) before the bias correction): with eps 0 Keras equals torch to
   6.5e-7 over 5 steps (float32 rounding); with eps 1e-8 the difference is 7.9e-6 (0.16% of the movement)
   (`test_update_rule_equals_torch`). Lion equals lion-pytorch to 4.1e-7.
4. Clipping: Keras scales by `clip / max(norm, clip)`, torch by `min(1, clip / (norm + 1e-6))`.
5. Past `total_steps` torch raises; `OneCycleLR` holds the last value. `pct_start * total_steps <= 1` raises (torch divides
   0 by 0 at step 0).
6. Weight decay `w -= lr * wd * w` in float32: 1 ulp from `w * (1 - lr * wd)`.

## TF32 decision

Decision: the train, eval and predict steps run under `jax.default_matmul_precision("highest")` (`TrainStep(matmul_precision=
"highest")`). Reason: HGQ2 emulates fixed-point arithmetic in fp32; a TF32 dot rounds both operands to an 11-bit
significand, while the production datalane (`kif` i0 4, f0 8) carries up to 12-13 significant bits, so products of
quantized values would not be exact, and the WRAP datalanes amplify rounding differences after the first mask feedback
(S3 deviation 8). JAX's DEFAULT precision with fp32 inputs is reported to run TF32 on A100/H100 (full fp32 on V100)
(JAX issue https://github.com/google/jax/issues/18934; a maintainer was unsure in https://github.com/google/jax/issues/19444),
so the setting is made explicit rather than relied on; not verified on a GPU here.

Measured on CPU (`S5_tf32_probe.py`, org test model, high and low specs): "default", "bfloat16" and "tensorfloat32"
give outputs identical to "highest" (max abs 0, 0 mask flips): the CPU backend ignores the precision setting, so the
size of the effect cannot be measured here. **Flag for G3:** on the A100, run the quantized forward and one train step
with "highest" vs "default" and record the output differences, mask flips and step time.

## Deviations from the plan

1. Read-out excludes the regularizer terms (above).
2. PeriodicEBOPs reproduction: the plan's 804.96 / 0.381 are the hybrid's double count; the gate is met on the
   deduplicated values (804.9104 / 0.33496), which the native reproduces.
3. The accumulation-equivalence gate uses the float org model with a per-event-mean loss and AdamW epsilon 1 (Adam and
   Lion are invariant to the gradient scale, so a mean-vs-sum difference is invisible at the default epsilon); the
   matched loss is not decomposable over micro-batches (weighted CE normalises over the whole batch), so for it the
   semantics is "mean of micro-batch gradients", as Lightning.
4. The training-port test keeps the hybrid's beta 0. The native driver must use beta > 0 for the read-out.
