## Decisions

1. **Arms.** hybrid-a and hybrid-b differ only in the train order (`data_seed` 42 / 1000042 in the native
   `EpochSampler(seed + epoch)`); same initial weights, config, controller, schedule. jax uses order A; jax-b (order B,
   GPU 3) is a diagnostic outside the verdict. The hybrid gets the native order through its own sampler (a copy of
   `EpochSampler.order`: `native_data` imports jax, which the hybrid env lacks; the test compares both).
2. **Same initial weights.** The hybrid writes a Lightning checkpoint at `on_train_start` (step 0); the converter
   turns it into the native warm start. Hybrid arms load its `state_dict` at `on_fit_start` (fresh optimizer, schedule,
   loops, controller), as `main_jax fit --init-from`.
3. **G4 config.** Production config (`03_make_config.py`, fp32, 1 device) with epochs of 500 steps x 10 = K 5000:
   with the production epoch (7769 steps) and PID warm-up 2 epochs the controller would never act within K.
4. **Verdict** (Erdem's decision 2026-10-24): JAX val loss at K inside mean +- 5.47 |A - B| (90% coverage of an
   exchangeable third run: `(2/pi) atan(c / sqrt(3/4))`, checked by Monte Carlo in the test); the strict [min, max]
   (33% coverage) is reported next to it; `--band` changes c. EBOPs: log10(EBOPs / setpoint) at K inside the same
   band with a 0.01 dex floor, or no farther from the setpoint than the farther hybrid. Preconditions: LR of every
   matched update within 1e-4, converted logits within 0.05 x max |logit|.
5. **Hybrid checkpoint steps never on an epoch's last step** (default every 96; JAX every 200). Measured: a resume
   from a checkpoint written on the last batch of an epoch skips that epoch's validation and the next epoch's
   `on_train_epoch_start` in Lightning 2.5.2 (`FitLoop.reset`, restart stage still set): beta stayed at init_beta after
   the resume (tiny run, kill at step 4 = epoch end, ckpt every 2). `check_ckpt_steps` refuses such intervals.
6. **Train set: full** (`--num-train -1`). Measured RSS of `CLICDataset` on the local `train_clic_fix.root`: 0.427 GB at
   20k and 1.366 GB at 80k events, 15.65 kB per event -> ~15.6 GB per process for the full set; pickle 6.6 kB per
   event. Worst case per node: 4 arms x (1 process + 4 workers) x 15.6 GB = 313 GB < 512 GiB per Polaris node (ALCF
   user guide, `docs/polaris/index.md`). `--num-train` gives a subset.

## Bug fixed: hybrid BetaPID lost its state on every resume

`hepattn.keras.callbacks.BetaPID` had no `state_dict`, so Lightning saved nothing for it: a resumed run re-seeded the
controller and its next step returned init_beta. This affects every resumed hybrid run (also `05_sweep.pbs` on the
preemptable queue). Test `test_controller_state_survives_a_checkpoint` fails without the fix
(`assert after == betas[3:]`); mutants m20 / m21 below.

## The step-1 train-loss residual (0.2-0.4%)

At step 1 (accumulation 2) JAX - hybrid was +0.095 on 24.8 (order A). With the LR set to 1e-30 and accumulation 1, the
loss of each batch at the converted init weights ([G4_evidence/step1_residual.txt](G4_evidence/step1_residual.txt)):
4 of 8 batches agree to <= 1.2e-6 relative, the others differ by 1.2e-4 to 3.8e-3. Batch 1 (the last micro-batch of
step 1) is the 0.38%: hybrid 24.82736, native 24.92240, the same numbers as the step-1 rows. Of its +0.0950, the final
regression L1 is +0.0825 (87%), mask BCE +0.0075, object CE +0.0034. Ruled out: data order (first batches compared
input by input: equal sums of every input), weights (converted bit for bit, class logits equal), LR (6.3e-7), matcher
solver (both `scipy.optimize.linear_sum_assignment`), what is logged (both: task loss of the step's last micro-batch).
Consistent with the documented S3 deviation 7: the regression proxy takes the top-2 particles per node, and with
quantized (tied) incidence values the set is implementation-defined (`torch.topk` vs JAX `top_k`, S3.md "tie"). Not
proven per row here. On Polaris the report's `early_agreement` shows the size at production scale.
